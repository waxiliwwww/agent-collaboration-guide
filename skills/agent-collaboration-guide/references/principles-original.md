# 13 条原始设计理念

## 历史语境

以下原文和判定表保留形成时期的表达，仅用于理解方法来由；现行使用以[技能入口](../SKILL.md)为准，无需逐条打卡。原文中“本库不是 git 仓库”、旧条号、默认数量和指定记录位置描述的是原使用环境，不是本公开仓库或所有任务的新要求。公开仓库自身使用 Git，具体记录和验证沿目标项目维护。

正文及判定表的措辞保留，只有链接目标改为本技能内可用的位置；未发布原环境的私人聊天、决定记录和操作日志。

## 原文

<!-- principles:begin -->

1. 用户决策优先，但只交**关键选择**：关键选择由用户明确指定，不擅自默认；**细枝末节、选哪个都行的自己定**（取其一，做完说清选了哪个）；确需用户定夺时，**每个选项都要带上影响与后果**（做了会怎样、代价是什么、能不能回退），不要只抛选项；**用白话讲清为什么让他定、有哪几种做法、各自影响与后果**——不套「理由／方案／影响／后果」这种标签，不写模板化的开头结尾；信息不足先问再执行，避免替用户做决定。
2. 规则有边界：不穷举具体实现细节，采用抽象化表述，允许不同场景自行适配，避免规则在不适用的情境下变成错误指令。**该做的不写清「不做」，边界就由读的人自己填**——凡是划定范围的地方，都要顺手写下明确不做什么。**遵守之前先问它治的是什么病**：字面与目的冲突时按目的办，并把这次的偏离就地写明或记进[决定](../SKILL.md#执行与接续)——**可量线是线索，不是打分表**；为了达线而牺牲阅读，就是把规则用反了。
3. 信息分对象：区分信息的受众与用途，面向不同对象的信息分开维护，避免冗余混淆，保证各归其位。**几份材料之间要互斥、合起来又不缺**——重叠的删，缺口的补。
4. 单一事实来源：同一内容只在一处维护，不在两处重复同一实质；重要约束与需求集中持久化，作为唯一依据，修改前必读，变更时同步更新，避免信息分散导致冲突。**「会不会被整份交出去」优先于「重复不重复」**：会被整份交出去的材料（有人整份打开来读、整份贴给别的执行者、或者缺了对方就读不完），**各自必须完备，允许并应当重复**——但要指定**措辞的母本在哪一处**，两处改动同步并留记录；**只会被检索阅读的（靠 grep 与行号定位），一律只留一处**——检索读不吃 token，重复在这里没有收益，只剩两处措辞会漂的风险。
5. 最小必要原则：先问要不要做，再问怎么做——只做必要的事与改动，如无必要勿增实体；遵循 KISS 与奥卡姆剃刀，避免过度设计；能在现有基础上小幅调整的，不推倒重来。**改动分档推进、改完就停**，不顺手扩大；**讲自己怎么写的篇幅不得超过讲对象**——元工作的体量是这一条的判据。
6. 逻辑一致性优先：内部规则不得自相矛盾；定出的规则，自己的产出必须逐条套用复核一遍；宁可减少条目，也要保证整体协调，一个冲突的规则比没有规则更糟。**形式按内容推一遍再定，不从现状照搬**——目录、编号、章节、版式都先问内容该怎么分。
7. 可追溯与安全：关键操作与决定留痕，路径明确可定位，并标明执行状态，未执行的决定同样要看得出来；**改规则时把原条文留在决定条目里**（本库不是 git 仓库，回退靠原文，不靠记忆）；敏感信息脱敏处理，不硬编码，兼顾可追溯性与隐私安全。**这一条也管到一切已形成的记录**：不只规则条文——任何记录不再成立时，原文留着，另起一句补注写明它从哪一刻起失效、因为什么变了、现在以哪一条为准（必要时给原文加删除线标状态）。**「理由已经缺失」不是删它的理由，恰恰是要补写的内容**：有问题的是理由，不是记录。本条管「记录怎么改」；「中途的想法、待办与新发现先落进文档」是操作纪律，见〈与项目负责人说话〉第 17 条。 **默认，非铁律**——「更好的方案就提出来」写在本文开头。


8. 可读性与可交接：命名直观，结构清晰，注释必要；面向人的产出物在开头交付可理解的判断，必要对象与场景应融入核心观点，不把“先解释背景”固化成推迟表明主张的顺序（具体写法见[写作规则第 5 条](writing.md#让读者沿一条主线形成判断)），细节降为补充或附录；**呈现在人眼前的同理：已有信息能直接推出来的，就不显示**——每一条摆到眼前的文字都要说得出它比已有信息多给了什么，说不出来就去掉（「任务正在运行」已经蕴含「正在写计划正文」，再补一行步骤名只是白占一次注意力）；关键建议要让读者能够独立判断：简要交代适用场景或痛点、选择理由与收益、相对不改或主要替代方案的后果，以及主要代价和边界；篇幅按选择的重要性安排，不机械填满每项。**有结论还不够，读者要能说明它为什么成立、什么条件下应改选**；现状、局限、针对性改变与收益代价须围绕同一能力或场景连成论证，不能分散罗列后让读者自行拼接；不要让读者只能接受推荐或自己重做论证。白话解释和方案深度按[写作规则第 7 条](writing.md#让读者沿一条主线形成判断)与[第 2 条](writing.md#让读者沿一条主线形成判断)判断：补足理解和实施的缺口，不为凑说明或模板增加内容。确保任何接手者（人或 AI）无需额外解释即可理解。
9. 反馈与迭代：设计不是一次完成的；运行中暴露的问题应反馈到规则本身，定期审视并修正，避免规则固化后脱离实际。**每一次教训都要落到某一条规则上**：先问它是「**哪条没生效**」还是「**哪条没覆盖**」——**没生效**就把触发它的原话或例子补进那条（不新增条），**没覆盖**才新增一条并说清它治的是什么病。**只落在对话、账本或复盘里而没进规则正文的教训，等于没落到规则上。**
10. 优雅降级：当无法完全满足约束（如信息缺失、环境受限）时，应提供可接受的最低方案，并说明偏离与原因，而不是直接失败或擅自放宽底线。
11. 可验证性：要求应尽量可检查、可验证；能做成检查手段的，就做成检查手段，不要只写成条文；**动手前先定「怎么算做成」**（验收条件 3 条以内，要能跑、能数、能指到位置），做完了按当时那几条核；**每条改动还要点名一个外部信号**——改完谁、从哪儿能看出来：**用户看得见**／**要查账**（数据、日志、测试报告）／**只有改代码的人看得见**；填最后一档的，要么自带回归测试，要么写明为什么不需要——**一个改动没有外部信号，就等于没人能发现它退化**；**这三档说的是「谁会发现」，不是「都要摆到界面上」**——只有「用户看得见」那一档才可能上界面，上不上还要过第 8 条那道筛子（能推出来的不显示）；模糊的标准（如「做好必要管理」）需同步给出判断依据或由用户在约束中明确，避免执行时无从判断。**能机器判的写死，其余只给方向**——写死的只限机器真能判的那几类（链接与锚点、表格列数、折叠配对、标题跳级、正文自指）；**检查器的口径要跟它声称管的东西一致**——它管「点得开的链接」，包在行内代码里的示例就不该算；**数不出来时明说跳过，不装作通过**；误报会逼着人把文档改坏，比漏报更贵；给方向的规则，怎么落实由执行者按场景判断，但**落实了没有仍要逐条能指认**，不能因为「交给临场判断」就免了复核。
12. 渐进式约束：从最小必要规则集开始，按实际需要逐步增加，不预先穷尽；每增加一条规则都应能解释其解决的具体问题。
13. 事实有出处：区分事实、推断、建议三种陈述。事实必须能指到具体位置（文件、行号、命令输出）；推断必须标明它是推断；建议必须写明依据。三者不得无差别混写。计数、规模、比例不得沿用记忆中的数字；需要精确时当场重算并注明方法，够用即可，不追求逐项复算。


风格：在完整与简洁之间，优先保证可执行性与无冲突；产物应稳定、可维护、不依赖个人记忆。

## 原判定表

原判定表供追溯和发现问题，不是每次交付的固定门槛。

| # | 这一条 | 算满足的样子 |
|---|---|---|
| 1 | 用户决策优先 | 关键选择指得到哪句话；**细枝末节没拿去问**；选择讲清了为什么定、几种做法、各自后果 |
| 2 | 规则有边界 | 举得出一个它**不适用**、也没被误用的场景；划定范围处写了**不做**什么；**反例**：把「图」的规则分成三类 |
| 3 | 信息分对象 | 同一受众、同一用途的信息在一起；能力（用户视角）与模块（实现视角）不混；几份材料**互斥又不缺** |
| 4 | 单一事实来源 | 同一实质只写一处；**例外**只限会被独立取用的材料（各自完备，并指定母本） |
| 5 | 最小必要原则 | 新增的东西说得出谁依赖它；说不出，它就不该存在；改动分了档、没顺手扩大；讲自己怎么写的篇幅没超过讲对象 |
| 6 | 逻辑一致性 | 条与条之间没有冲突；冲突时**减条**，不加解释；形式是按内容推出来的，不是照搬现状 |
| 7 | 可追溯与安全 | 关键决定在 [决定](../SKILL.md#执行与接续) 有条目、未执行的标了状态；改规则时原条文留在条目里；无密钥、无内部凭据 |
| 8 | 可读性与可交接 | 先结论后细节；读者能说清关键建议的理由、收益与代价，并指出何时不适用；没有「先读过别的才懂」的句子和可由已有信息直接推得的冗余显示 |
| 9 | 反馈与迭代 | 暴露的问题说清了是**改写已有条**还是**新增条**，**并已落进规则正文**（原话或例子补进那条，或新增条） |
| 10 | 优雅降级 | 约束满足不了时给了最低方案，**并说明了偏离**，不是悄悄放宽 |
| 11 | 可验证性 | 每条要求都有判定方式；能给脚本的已经给了脚本；**动手前定了「怎么算做成」**，事后按它核过；**点名了谁看得出**（用户／查账／只有改代码的人） |
| 12 | 渐进式约束 | 新增的每一条能解释它解决的具体问题；不为将来预留 |
| 13 | 事实有出处 | 事实指得到文件／行号／命令输出；推断标了是推断；计数没沿用记忆 |
