# 写作与机制解释

写给谁看，读者想知道什么，决定文章怎么写。用户已有具体问题，先回答问题；介绍一个系统，则先说明它做什么、由哪些部分配合。需求和授权仍按技能主文处理，不增加固定篇幅、图数或问卷。

<a id="起草前先设计读者怎样建立理解"></a>

## 先确定读者和写法，再起草

先读用户的问题、已有材料和认可的内容，确定读者需要哪些背景。标题承诺介绍整个机制，就要覆盖主要过程和常见变化；可以从简单例子讲起，但不能让一个例子冒充全貌。深浅按理解和实际使用的需要安排，不等用户逐项指出遗漏。

审查、精简或重写已有内容时，先按[内容取舍与逻辑审查](content-review.md)核对目的、依据、重叠、冲突及读者理解，再处理表达。需要进一步改善文风时，检查可用技能。[human-writing-skills](https://github.com/whh110112/human-writing-skills) 是一个具体候选：读它的 SKILL.md，再只选适合技术说明、报告及原文保真的模块；不把小说用的细节描写和节奏规则套进技术文档。未安装或没用过，要说清楚，不能把放了链接称为已经使用。

写的时候说明谁做什么、根据什么处理、结果会怎样。比如"完成关联交接"可以改成"改完接口后，同时修改调用它的页面和测试"。"固定范围和完成依据"可以改成"写清这次改哪些功能，怎样判断做完"。术语确有必要就保留并解释，不用一串抽象名词替代动作。

正式、准确的文字也可以自然，不必故意口语化、编故事或制造细节；不为句式整齐强行合并不同问题。

<a id="正文把因果与实现手段连起来"></a>

## 用过程解释机制

机制说明开头先讲清现在怎样处理、关键规则和后果，后文再解释原因和实现。每次可以讲一层，但讲到跨层依赖时要补够背景，不提前铺满所有细节，也不省掉关键前提。陌生术语第一次出现时解释。

读者要知道：为什么需要它，什么会触发，谁拿到什么，根据什么判断，怎么处理，结果交给谁，失败后怎么办。"保存、恢复、匹配、加载"要说明实际对象和处理过程，不能只换成几个白话词。

选一条有实现依据的过程，把数据怎样产生、保存在哪里、靠哪些标识关联、何时读取、缺失或不匹配时如何处理讲通。理解必需的标识、关系和失败处理留在正文或图中；完整字段、函数和源码放查阅部分，折叠细节时别藏掉必要解释。

先讲正常过程，再改变常见条件，说明同一套规则如何得到不同结果。一个分支只代表它自己。发现例子与总述矛盾，回头修整篇的解释和图，不只追加一条例外。

## 图表帮读者看清关系

在写正文时一起设计图，不等写完再装饰：

| 读者需要看什么 | 可用什么 |
| --- | --- |
| 组件、接口、归属和存储位置 | 架构／关系图 |
| 谁先做、等待谁、何时保存或通知 | 时序图 |
| 哪些条件会导致哪些结果 | 流程／状态图 |
| 多个对象同时工作或竞争资源 | 泳道／并发图 |
| 条件、方案、证据之间的差别 | 表格 |

图上写实际传递的内容、接收者和关键判断，检查顺序与依赖。逻辑职责、运行进程和代码目录不是同一回事，分别说明。正文补原因、背景和后果，不把整段文字搬进方框，再重复解释一遍。小事实直接说，不凑图种。

<a id="研究与方案证据支持有条件的判断"></a>

## 判断需要证据支撑

先对照用户要求，说明能力是否实现、缺什么；再区分目前启用了多少、验证了什么、后续扩展要做什么。还没有具体新版本或插件，不等于通用机制没实现；只有测试实现，也不等于真实新版本已经可用。

检查实现要追到实际使用数据或能力的地方。接口存在、数据写入、恢复时确实读到，是不同证据。设计目标、待选方案、理由与推断单独标明；反常行为要有依据、理由或明确未知，不能用"代码就是这样"证明设计合理。

涉及外部动作时，区分未开始、已经发生、确认收到和结果未知。解释重试何时查询、复用、覆盖或拒绝；持久记录与缓存、文件引用与真实文件、查询材料与执行动作分别说清楚。

调研时先看原始资料、真实接口和现有能力，再比较现状、最小改善与值得考虑的替代方案。说明怎么接入、能改善什么、要付出什么、什么条件下会改选，不编弱方案陪衬。实际引入第三方内容时核对许可、依赖与运行条件。

数量交代定义和分母，测量附真实数据、版本、条件与方法；估计和模拟要标明，未知不能当作零或不存在。声称更好或已经改善时，要有对应结果支持；没有证据就说明能力和限制。不能在缺少同条件比较时编排名。可能推翻结论的反例优先查，不为无关枝节无限搜索。

科学图表用真实数据、单位和标准绘图工具，不能为画图编数。引文核对原文和发表状态，预印本、同行评审与社区经验分开，按任务格式引用。

<a id="修订与交付审查理解不只审排版"></a>

## 修改后从读者入口再读一遍

收到"太多、太空、看不懂、前后接不上"等反馈，检查是不是少了背景、对象、条件、因果或实际例子。保留仍有效的文字、图和查阅位置；不要只缩字数、加卡片或换一批术语。同类纠正再出现，先检查整篇有没有同样的问题再扩写。

从标题和原始请求出发，判断读者应该能回答哪些问题，再读正常过程及必要变化。每个模块间是否接上，关键依据是否能直接找到，核心结论是否还要读者自行跨段拼接。代码和证据注明版本与条件。能取得独立审阅时，让审阅者先看原始任务和成果，不先提供作者清单。

实际打开成果，检查图的连线、字距、图文、交互和取回路径。源码核对、页面展示、运行验证和用户认可分别说明，检查通过不能证明读者理解。确需代表片段校准时再做，已有方向不重开确认，也不要求用户参加阅读考试。

成套文档按读者任务保留稳定入口，新材料改回原位置；另存修订保留主名和版本。局部改动遵守原格式与范围，写前检查用户是否手改过。链接、锚点、生成入口和独有内容一起维护，不只搬目录或拼成长文。

<a id="规格合同与正式成稿"></a>

## 规格、合同与正式成稿

按确认模板与授权写，保留指标精度；未知资料注明待确认，不能从实现擅自增加参数、端口或义务。正文写对象、要求、机制、接口及必要限制，讨论和后续计划留任务记录，除非用户要求包含。方案、实现、验证、运行生效和业务验收分别标明，改名或演示不能代替实施。
