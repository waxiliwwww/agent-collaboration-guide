# 文档与写作

适用于技术设计、项目改进、调研报告、合同与规格材料，以及既有文档修改。独立交付的报告、调研和说明性文档，未指定格式时默认使用可直接在浏览器打开的 HTML；仓库维护文档、技能源文件、已有模板及用户指定格式沿相应约定。依用途选取相关部分；查阅清单、账本和原文摘录以准确检索为主，不强求叙事、摘要或图表。

## 让读者沿一条主线形成判断

动笔前想清楚读者要作出什么判断，把主张和支撑它的方案想具体。开头交代对象、问题及必要语境，尽早给出核心判断和理由；不熟悉项目的读者也应知道为何值得继续读。摘要压缩完整论证，保留关键前提、收益、代价与边界，正文增加机制、例子和依据。短文不必另设摘要。

按问题、对象或使用场景组织成品，讨论先后顺序不直接成为目录。同一判断集中讲清，沿同一个例子说明当前限制、改变机制和结果差异。正文先突出影响判断的少数核心点；不把核查过程铺成正文，不用长表格承载整段解释，能用短段说明就不用表。字段、命令、来源细账等放补充层，关键机制和限制仍在正文可见。追问理解缺口就补正文，追问实施细节就补对应层；只有细节改变判断时才连带调整摘要。分层和折叠用于降低阅读负担，同义复述应合并删除。

图表用于解释关系或比较，附近文字交代核心判断及易误读之处。标明现状、目标或概念示意，统一对象名称，区分依赖、调用与数据流；复杂图先给主关系再展开。核对实际渲染、文字与连线可读性，兼顾明暗主题；环境不支持时用可读替代。数值图交代真实数据、单位和刻度，不为画图编造坐标或评分。

## 技术设计与项目改进：先讲通正常过程

设计先沿一次正常任务讲清：什么触发，输入从哪里来，谁按什么依据处理，结果怎样产生并交给谁；再展开职责、异常和实施细节。 同一使用要求应能关联到概念职责与状态、技术实现和验收证据；执行发现新问题时，先回到用户目标判断合理做法，再修改受影响的需求与设计，不以代码现状反推用户必须接受的行为，也不为局部反馈重写全套方案。职责解释谁负责什么，时序解释何时发生和依赖什么；配置说明设定了什么，执行说明何时读取并生效；动作完成与内容正确分别取证。涉及这些区别时说清即可，不必各建章节。

将“易扩展”落到修改入口、兼容影响和代价，将“可验证”落到谁检查什么、凭什么判断。总体方案讲清边界、共享关系、取舍和验收；先深入最可能推翻判断的关键机制，再按风险细化子模块。支持实施的部分应说明触发、输入输出、状态变化、失败去向与测法，使接手者无需补上关键决定就能开始实现或构造样本。认可总体方向不等于子机制已验证。

多模块或多文档设计，沿同一任务核对交接：上游输出是否满足下游，调用、等待和状态提交是否一致，失败由谁接回。细化改变职责、接口或保证范围时，回查总体图、主时序、摘要及验收；摘编日报、汇报和重绘图也须保持这些关系。冻结材料只读对照，指出冲突、影响及现行依据，不能仅因原文未改就称整体一致；未处置的关键矛盾保留为缺口。

改进论证接通“已有能力与具体限制—改变机制—场景收益—成本和边界”，比较保留现状及最有竞争力的替代方案。不把已有能力包装成新增价值，不把源码可见风险说成已发生故障；无基线时给测法，收益待测。当前够用或低频小规模时，说明简单方案的优势。

## 调研分析：从问题走到有条件的建议

适用于综合资料、解释机制、比较路线或提出建议；窄事实查询和已有充分依据的简短答复直接回答。先明确读者最终要理解什么或作出哪个决定，再确定所需证据。先理清概念、对象与层次，按问题寻找相关路线及反例，允许新证据修正最初分类。优先核对原始文档、论文、协议、源码或实际记录；说明样本为何可比、借鉴什么、未覆盖什么。“开源、知名”本身不能代表主流。

比较使用相同的任务、约束、版本和统计口径，保留无法抹平的条件差异。核对各方已有能力，共同点不算某一方独有优势；官方宣称、源码可见、实测结果与推断建议分清。未知不填成否定或零，来源冲突先核对对象、版本及条件。评分需有尺度和权重，没有共同测量就不作效果排名；测量注明对象、版本、条件与方法，估计和预算不作实测。来源就近支持判断，动态关键资料按需保留原文，访问日期不等于历史快照。

先做透最影响判断的一项，再扩展：观察到什么事实，什么机制能解释它，在目标场景下产生什么影响，因此在什么条件下怎样判断。机制不明就查证或验证，不用“更灵活、更可靠”等形容词补空。再检验最强替代、反对证据及改选条件，使限制实际影响建议。可以形成推荐、分场景选择、争议解释或暂不能判断，不强造赢家，也不为展示过程刻意推翻原观点。未知会改变下一步就优先补查或有限验证，否则说明影响后停止扩搜。多个建议有关联时，用同一场景解释配合顺序。

例如，以下均为假设，正式调研须核实：任务是判断是否替换现有接口适配器，必须保留旧调用方。拟查的证据包括双方协议版本、字段语义、错误与取消处理及维护成本。假设新方案支持相同成功结果，但把“取消”折算成普通失败，那么成功样本不足以证明兼容；依赖取消状态的调用方可能继续重试。若旧方案仅缺一个必要字段，局部补齐更省迁移成本；若新方案能保留取消语义且显著减少维护，才有改选依据。下一步用一条成功请求和一次取消贯穿真实调用方，检查返回内容、状态和副作用，而非先宣布整体替换。

卡住时区分缺口：证据不足就补材料或收窄结论；因果未通就追机制或做验证；范围过宽就回到待决定的问题；只有表达不清才调整结构和措辞。报告要让读者知道为何推荐、何时不适用及怎样继续，不能以润色替代判断。

## 合同、规格与验收材料：守住依据和责任

沿已确认模板与用途写可审阅草稿，未知专业资料不阻塞能确定的部分。合同正文、技术附件和约定范围的需求稿，以能力、接口关系、交付内容、责任、必要依赖和验收要求为主；保留原合同指标及技术细节的精度，其余不提前写死端口、框架版本、内部字段、备份机制等实施参数，不使其自动成为新增义务。详细设计和测试报告按其用途给足具体方法。

对照实际提供的合同、规格及有效变更，保留指标对象和统计口径。未见正式合同就说明实际依据；代码与工程说明用于判断能力，不自动变成合同要求。引用真实文件名、版本与日期，不能将查阅日期当发布日期。

分清技术执行、项目统筹和专业判定责任，说明上下游输入及协作条件；同一人兼任多个角色也不无条件兜底专业结果或整体指标。不新增成功率、时延、并发、可用性或任意接入、任意恢复承诺，不降低原合同义务；原有高风险要求保留并说明待评估问题。

未知业务接口先写接入能力、必要条件及责任，不虚构流程或穷举字段。模板需要时可给标明适用模块、前提和可调性的参考配置；无依据或实测不称最低达标配置，软件本体与模型推理、专业计算等资源分清。不适用写明不适用，适用但未知的专业公式、容差、身份信息等保留待定，不能为填满而编造。

正文呈现已确定的要求和必要条件，讨论事项留在对话或已有清单，答案确定后融回正文。交付复核有无新增承诺、遗漏原要求、越出责任范围或把参考配置升级为验收门槛。示例脚本和工程链路跑通不能充当真实业务或专业结果验收。

## 修改、版本与实际产物

局部修改或按模板填写，保留原格式、结构和范围外内容，必要新增正文复用原样式；不擅自改目录、重排版或增加附录。以用户实际最新手改稿为基础，写出前再次核对，避免旧稿或生成器覆盖新调整。原件需保留时另存。

另存交付的迭代稿保持稳定主名，以 `_v0.1`、`_v0.2` 等后缀递增；已有项目编号则沿用。保留原件和已有版本，不以“最终版”或仅日期代替版本号；固定仓库入口、事实母本和历史证据不因此改名。版本号表示修订次序，不表示批准。

交付前重新打开实际文件，对照基础稿检查内容及格式差异；长文重组确认独有事实和历史证据仍可定位。必要时请未参与起草者先从原始任务独立提问，避免沿作者提纲重复自查。

## 学术材料的引用与修订

按任务或投稿格式写作，核实原文、发表状态和引文所支持的范围，不编造文献、数据或证据。优先使用适合论点的同行评审论文、学术书籍和官方报告；预印本明确标注，检索平台不等于同行评审，博客或百科等不能单独承担核心学术论据。

无指定格式时，按首次出现顺序编号引用，同源复用同号，文末给作者、年份、题名、发表载体及 DOI 或稳定链接，核对书目对应；图表注明真实来源，单位与术语一致。修订按审阅需要标记实质变更，交付版本沿上节处理。
