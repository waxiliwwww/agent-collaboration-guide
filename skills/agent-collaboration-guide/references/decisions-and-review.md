# 决定、偏好与反馈闭环

用于跨轮决定、重复纠正、复盘和技能维护。普通小事直接按当前对话完成，不另建台账，也不要求每轮记一遍。

<a id="一份当前依据"></a>

## 只维护一份当前记录

先找当前任务或项目的需求、决定、Plan 与待办，保留目标、范围、约束、状态和下一步。明确反馈区分补充、替换与取消，更新同一依据；保留替换来由，旧记录不能阻止用户明确的新要求。未决的重要取舍在对话中提出，不能只写进文件后继续。

确认边界沿[总入口](../SKILL.md#开始先形成完整骨架)：已有决定且前提未变就沿用，只对未覆盖的重要变化重新对齐；例行检查、可查事实和授权内可逆细节不转嫁用户。项目规则是默认方法与评判依据，可提出更好做法，须比较实际后果；偏离不绕过上级要求、用户决定或重要取舍确认。

<a id="反馈写到哪里"></a>

## 反馈记在哪里

| 反馈的性质 | 保存位置与生效方式 |
| --- | --- |
| 本次目标、决定、待办或事实修正 | 当前任务／项目记录；保留本次范围 |
| 用户明确的长期选择或更正 | 私有 `local/preferences.md` 或其专题；及时写回，下一相关任务读取 |
| 根据行为提出的理解假设 | 私有观察，标为待验证，不改变稳定偏好或授权 |
| 可复用的通用方法候选 | 先脱敏并记录适用条件、证据、反例与代价，经维护审查再吸收 |

私有条目只需足以查到当前有效选择、适用范围、来源时间和替换状态。入口留短索引，项目或场景细节按需拆分；不复制整个聊天或公共方法。无信息就不猜，不因一个任务顺利或用户未回应就推断认可。

<a id="闭环如何运行"></a>

## 收到反馈时怎么做

1. **触发。** 用户明确肯定、否定、更正成果或要求沉淀时，主动归纳并核对已有约定；同类问题重复或主要阶段收口时，也检查是否已有值得复用的新信息。不等用户另行要求"更新偏好"，也不把每次反馈变成一次问卷。
2. **查原因。** 检查规则是否缺失、入口是否能发现、是否未执行、检查是否只验了局部。先修当前成果与已有规则，不把个案措辞直接加进长清单。
3. **写回。** 按上表保存；同类内容合并，被替换内容移到历史。起草、发布和安装分别沿本轮授权，不把维护许可扩成任意外部动作。
4. **下次用起来。** 下次相关任务开始／恢复时读有效项，将原目标、必要影响和完成判据落实到现有 Plan 或任务依据，并在交付时逐项核对。纠正后检查整条关联逻辑，避免继续逐点补丁；只读过规则、写回偏好或给出承诺不算执行证据。
5. **检查是否有帮助。** 有适用任务时观察是否减少同类纠正和遗漏，同时看阅读、等待与维护成本；效果不明就保留未知，无效规则撤回或重写。不要以规则变多、记录已写或 AI 审阅通过宣布改进成功。

## 肯定反馈怎样处理

先判断用户认可的具体对象：内容、组织方式、操作效果或本次结果。按其明说的范围记入当前任务，不能把"写得清楚"推成全部事实、代码或运行结果都已验收。

随后核对现有偏好：已有约定能解释这次认可，沿用并可将成果作为本次认可的参考，不新增同义条目；用户明确要求以后沿用或保存，按其范围直接写回；只有 Agent 新归纳出实质不同的长期做法时，才简述观察、适用范围和未来改变，取得确认后升级为有效偏好。未确认只留本次依据或待验证观察，不静默改变默认行为或授权。一般赞许没有新的可执行信息时，正常回应即可。

## 总结的时机与方式

主动总结不是每次交付的固定步骤。仅在已经出现值得跨任务沿用的新经验、反复摩擦或明显的做法变化时，选主要阶段收口集中提出；同一阶段不反复拆成多轮总结确认，没有实质新内容就不问。

提出时先给结论：简短说观察到了什么、适用范围、以后会改变的做法，例如："我从这几次反馈归纳出 X，拟在 Y 场景采用 Z。这个理解准确，是否作为以后约定？"要说明以后会改什么，不泛问满意度，也不要求用户重讲经验或给技能打分。

- 用户已经明确要求保存、说明长期偏好或更正时，直接写回并告知，不再问同一件事；明确要求总结时完成总结，只确认仍属推断或范围未明的部分。
- Agent 新归纳的长期选择，经确认才升级为有效偏好。未答复只保留待验证观察，不当作同意，不催问；不依赖该选择的工作继续。已有确认仅在新证据或适用范围实质变化时再提。
- 实际用技能解决范围、组织或验证问题时，在首次采用或关键阶段简短点明相关做法；不逐条引用规约、不每轮播报，也不把修改记录当作效果证明。让用户看到实际改变，并保留是否认可的判断权。

不设默认定时复盘、每轮索评或机械满意度问卷。总结确认、执行审批与用户验收各有目的，不能合并成多余的批准关卡。

## 什么能从偏好进入公共方法

候选应有超出某个用户／项目的明确机制、适用边界和合理代价，能解释旧规则哪里不够或为何没触发；去掉身份、路径、个人格式、固定数量与特有授权。已有通用条款可承接时直接合并，不增加同义条款。

明确的用户选择仍可立即在本机使用；公开吸收不等于普遍效果已验证。复杂修订用未参与起草者按原始请求审阅，必要时给未见过的代表任务进行前向演练，不喂预期答案或已知漏洞，再按实际结果修正。结构检查、行为样例、用户接受与持续收益分别说明。

公共条款已承接的方法从私有常驻偏好移除，私有层只保留用户具体选择和必要来源。历史另存可追溯，不默认加载。个人选择和私有记录存放在安装目录的 `local/`，更新时保留。

## 独立复核怎样避免共同盲点

复核者先看原始任务、关键反馈、有效决定与实际成果，自行确定主要判断，再核查实现和差异；不只审作者摘要。看常见入口、生命周期、数据／执行交接、失败后果及保留成果，也检查多余确认、无用记录和转嫁工作。范围按风险裁剪，不要求多名 agent 各填同表。

发现问题指向具体依据和影响；修复后定向复核，保留首次问题与分歧，不能反复审到得到有利意见。没有所需独立意见或仍有实质分歧时说明，不自行视为通过。
