# 设计取舍、来源与比较

本项目把一次任务的协作组织为“先对齐使用预期—沿约定执行与接续—用实际成果验收”。它来自反复发生的方向误解、范围漂移、上下文遗忘和验收不足，也吸收了已有公开方法。

## 为什么这样组合

**需求允许是软的，下一步行动应当有依据。** 用户不必先写出规格书。智能体先核查事实、提出使用场景和可选路线，再询问会改变方向的事项。讨论结果可从一段话逐步长成方案，而不是先让用户填表。

**简单与完整共同决定实现。** 规划考虑长期运行及可预见失败；实施以本轮已确认目标为边界，优先复用已有接口。最简不能删掉承诺能力，考虑周全也不自动授权所有未来功能。

**记录让协作可接续。** 当前需求、设计、任务和反馈沿一份已有依据维护。恢复时读未完成事项，不靠用户再解释一遍；重要变化保留来由，普通小修不增加台账。

**验收从用户实际过程出发。** 章节齐全、工具执行成功和用户能够完成任务是不同证据。检查按改动风险先局部、后必要组合，保留首次失败和未知；评价协作收益时也看用户介入、等待和维护负担。

这些取向组合起来构成本项目的特点。它们不是独占发明，也不能仅凭写进技能就视为已实现。[验证边界](evidence.md)说明了目前的证据。

## 实际参考与互补关系

以下资料于 2026-10-27 重新核对。它们包括开源工具与公开文档，不统称为“开源仓库”；概念借鉴不表示打包了其实现，也不表示获得作者背书。

| 来源 | 参考或比较的内容 | 在本项目中的取舍 |
| --- | --- | --- |
| [Matt Pocock 的 grill-with-docs](https://github.com/mattpocock/skills/tree/49dd158d1076134a641b33efb035946536778336/skills/engineering/grill-with-docs) | 主动访谈，结合 grilling 与 domain-modeling 澄清方案、术语和决定 | 采用主动提问思路，问题限于当前决定；已有记录优先，不默认建立 ADR 或术语表 |
| [Spec Kit](https://github.com/github/spec-kit) | 规格驱动及其他可组合工作过程、模板、约定与验证 | 需要正式规格与自动化工作流时可以沿用；本技能承担协作取向，不再建第二份规格 |
| [OpenSpec](https://github.com/Fission-AI/OpenSpec) | 变更提案、规格、设计、任务与归档的联动 | 已采用 OpenSpec 的项目直接复用其变更材料，避免反馈只留在聊天里 |
| [Kiro Specs](https://kiro.dev/docs/specs/) | 需求、设计、实施计划之间的联系 | 保留各自用途，文档数量按任务深度决定；这是公开产品文档参考，不称为复制开源代码 |
| [Diátaxis](https://diataxis.fr/) | 按读者需要区分教程、操作指南、参考与解释 | 人读 README、智能体读技能、场景按需展开；不把四种文档形式变成每项任务的必填目录 |
| [arc42](https://arc42.org/overview/) | 架构的目标、约束、上下文、运行视角、决定与风险 | 设计解释正常过程、关键交接和取舍；按需借鉴，不照搬十二节模板 |
| [Agent Skills](https://agentskills.io/specification) 与 [OpenAI 技能说明](https://learn.chatgpt.com/docs/build-skills) | `SKILL.md` 元数据、按需读取与参考目录 | 使用标准技能形式，只保留本技能实际需要的文件；没有附加运行服务 |

本轮是根据这些一手材料所作的方法比较，不是同任务、同资源的产品效果排名。Spec Kit 和 OpenSpec 也支持灵活迭代，不能以“其他工具都僵化”作为本项目优势。

## 怎样选择

- 想改善“怎么问、怎么拍板、怎样持续推进和验收”，可以从本技能开始。
- 需要规格变更、任务生成、团队流程或自动化工具链，优先看 Spec Kit、OpenSpec 等既有工具，按项目需要组合。
- 已有良好的项目规约和执行机制，只补必要缺口；不必为了采用本技能迁移现有文档。

## 演进与维护

公开版来自协作规约 1.1.0 的一次适配：去掉私有工作区路径和本库操作入口，把通用方法放进 `SKILL.md`，保留三个场景与 13 条历史理念。历史理念正文只改链接目标，原文中带有原使用环境和数量约束的表达由说明明确限定为历史资料。

本仓库是公开版维护入口。更新时先比较来源版本与公开适配，保留有效差异；每条补充应说明解决的实际问题。优先删除重复、修正触发和消除冲突，而非用新条款覆盖旧条款。
