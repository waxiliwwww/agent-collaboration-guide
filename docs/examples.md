# 使用示例

以下是说明方法的假设对话，不是效果实测或固定话术。

## 模糊需求：想做一个任务监控

用户：“帮我做个监控，别总让我猜它在干什么。”

智能体先查已有任务状态和日志，再交流：“我理解你最需要的是知道任务是否在推进，以及失败后怎么办。现有状态接口能提供这些信息。建议先在已有任务页补开始时间、当前步骤与异常原因；单独建大屏会多维护一个入口。你主要自己查看，还是需要别人持续值守？任务停滞时希望怎样处理？”

用户明确使用预期后，智能体简述本轮范围、正常与失败结果、完成条件，再实施。图表、通知渠道或新平台只在确有需要且获同意后增加。

## 明确小修：修改一处提示

用户：“把这个‘同步中’改为‘正在保存’，其他不变。”

智能体核对实际界面及相关文案，完成改动并检查呈现。无需重新访谈、写规格或展开架构方案；若发现改变会影响另一种状态语义，才说明差异并确认。

## 分支冲突：保全两边的有效改动

用户：“把这个分支合进来，另一边的修复别丢。”

智能体从共同基线分别检查双方目的，逐步解析冲突及关联改动。一边修复取消状态，另一边调整重试，不因新代码更长就整块选用。两者可兼容时整合并验证交互；若对取消是否允许重试存在实质分歧，先给影响、选项与推荐，请用户确认。

没有冲突标记也检查调用方、默认配置与有意删除。PR 描述交代最终保留了什么、验证到哪，不能以“可自动合并”代替行为保全。

## 长任务恢复：沿用已确认内容

用户：“继续昨天的改造，另外新增一个导出格式。”

智能体读取原任务依据和全部未完成项，说明现状。原来已批准的目标继续沿用；新增格式写回同一需求与计划，判断它是否改变交付范围、关键设计或验证条件。仅对新增的未定事项提问，不丢掉昨天未完成的部分，也不让用户重说全部背景。

## 补齐交接：两种入口与有效决定一起检查

项目已有决定：“技能支持上传包与 Git 两种入口，作用于当前项目，更新由用户手动发起。”该决定及来源保存在项目现有设计中，任务计划引用同一处。

用户：“修复导入成功后当前会话找不到技能的问题。”

智能体先读已有决定与计划，核对两种入口的保存位置、发现和加载路径，以及失败后留下什么。必要的消费者和配置衔接在本轮补齐，不重新询问是否支持已确定的入口。若发现自动同步可能改善体验，先识别它会改变既定范围，只在确有必要时带收益、代价和替代建议请用户判断；不顺手加入。

交付时核对两条已有路径的实际结果，独立复核者还能从改动反查是否暗中改变项目作用域或手动更新约定。用户以后明确采用自动更新时，更新原决定的范围、状态与替换关系，不把旧结论永久冻结。

## 统计报告：让数据支持判断

用户：“分析任务失败情况，帮我判断先修哪里。”

智能体先核对数据、失败定义与可比较口径，展示关键指标和必要的类型对比或趋势，解释优先建议及局限；比例交代分母，未知与零分开。少量数值可用表格，不强制凑图。证据明细可追查，用户不必从长段文字中重组统计关系。
